## Context

F02-US02 targets type-safe API contracts for frontend consumers. F01 created the monorepo package shape, and F02-US01 left the API exporting `./registry` and `./data` generated by Tuyau from `apps/api`. However, `packages/tuyau` is still a placeholder, while ERP, CRM and PDV keep app-local stub clients under `src/lib/api.ts` and comments describing a future Tuyau migration.

The frontend apps are Vite React apps. They do not currently declare `@supexon/tuyau` as a dependency and do not have app-local `.env.example` files documenting a shared API URL variable. The scope here is to establish the typed client boundary and usage standard, not to replace all mock-backed feature screens with real domain API calls.

## Goals / Non-Goals

**Goals:**

- Turn `packages/tuyau` into the shared API client package for frontend apps.
- Use the generated API registry/data exports from `@supexon/api`.
- Provide deterministic API base URL resolution for Vite apps.
- Make ERP, CRM and PDV import the shared client boundary instead of maintaining independent API stubs.
- Add a repository guard against direct `fetch` or app-local HTTP clients in frontend source.
- Document the frontend API consumption pattern and update only F02-US02 RFC evidence.
- Prove focused typecheck/build commands for the touched package/apps.

**Non-Goals:**

- Do not implement new backend routes, controllers, validators, or domain CRUD.
- Do not replace all mock-backed screens with live data fetching.
- Do not introduce auth/session token persistence beyond the typed client boundary.
- Do not edit generated API registry/data files manually.
- Do not mark F03+ work complete.

## Decisions

### Keep `@supexon/tuyau` as the single frontend API boundary

`packages/tuyau` should export the configured client factory, default client, API data types, and base URL helpers. Frontend apps should import from `@supexon/tuyau` instead of importing `@tuyau/core` or `@supexon/api/registry` directly.

Alternative considered: configure Tuyau separately in each app. That duplicates base URL logic and makes the "no manual types" rule harder to enforce.

### Resolve base URL from Vite env with an explicit fallback

The shared package should expose a base URL resolver that accepts an optional override and otherwise reads `import.meta.env.VITE_API_URL`, falling back to `http://localhost:3333` for local development. Each frontend app should document this variable in its own `.env.example`.

Alternative considered: hardcode `/api` for all frontends. That is useful behind a reverse proxy but unclear in local multi-app development where API and Vite run on different ports.

### Keep app-local `src/lib/api.ts` files as thin re-exports

ERP, CRM and PDV can retain their existing import path as a compatibility shim, but the implementation should re-export the shared client package. This reduces frontend churn while removing app-local client behavior.

Alternative considered: update every screen to import `@supexon/tuyau` directly immediately. That is broader than F02-US02 needs and risks touching mock-backed screen logic before domain APIs exist.

### Add a simple repository guard before a full lint policy

Because app lint scripts are placeholders, add a focused check script that scans frontend source for direct `fetch(` and app-local HTTP client creation outside approved shared client files. The guard should be easy to run in CI and as part of validation.

Alternative considered: configure ESLint custom rules now. That is heavier than the current repo lint maturity and would mix lint foundation work into the API contract change.

## Risks / Trade-offs

- Generated API contracts may be stale -> Mitigation: run API build/codegen workflow through source commands and never edit generated registry/data manually.
- Tuyau package may need browser-safe access to `import.meta.env` -> Mitigation: keep environment access in a small helper and verify `@supexon/tuyau` plus each Vite app typecheck/build.
- Guard script could flag legitimate code -> Mitigation: scope it to frontend app `src` paths and document explicit allowed files.
- Thin app re-exports may not prove real domain consumption -> Mitigation: this change only establishes the shared contract boundary; actual domain data replacement belongs to later user stories.

## Migration Plan

1. Update `@supexon/tuyau` dependencies and exports to use Tuyau and `@supexon/api` contracts.
2. Add base URL helper and configured client exports.
3. Add frontend app dependencies on `@supexon/tuyau`.
4. Replace ERP, CRM and PDV `src/lib/api.ts` stubs with thin shared-client re-exports.
5. Add frontend `.env.example` files documenting `VITE_API_URL`.
6. Add the direct-fetch/client guard script and wire it into root or package validation.
7. Add documentation for frontend API consumption.
8. Run focused typecheck/build/check commands and update F02-US02 RFC checkboxes with evidence.

Rollback is a normal commit revert. No production data or database migration is involved.

## Open Questions

- Should the shared package export only a client factory, or both a default client and factory?
- Should the direct-fetch guard live as a root script, a package script in `@supexon/tuyau`, or both?
