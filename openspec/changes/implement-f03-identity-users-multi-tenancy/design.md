## Context

F03 in `docs/rfc-mvp.md` is the first change that turns the existing identity tables into a tenant-aware runtime boundary. The API already has AdonisJS auth, `Tenant` and `TenantUser` models, `TenantTransformer` and `TenantUserTransformer`, and many future domain tables already include `tenant_id`. What is missing is the request contract for active tenant selection, the membership/role enforcement layer, and database-level isolation through PostgreSQL RLS.

This change is security-sensitive because all later domain endpoints depend on tenant context being correct. It should stay API-only and source-owned: generated `.adonisjs/**` and `apps/api/database/schema.ts` may be regenerated by commands, but fixes must be made in source routes, controllers, validators, middleware, migrations, services, policies, and tests.

## Goals / Non-Goals

**Goals:**

- Provide authenticated tenant management routes for creating tenants and listing tenants accessible to the current user.
- Provide an explicit active-tenant selection contract that can be used by frontends and future domain endpoints.
- Persist active tenant context for the duration of each request after verifying the authenticated user belongs to that tenant.
- Provide membership management routes scoped to a tenant with initial role enforcement.
- Define `owner`, `admin`, `operator`, `seller`, and `viewer` as the supported membership roles.
- Set PostgreSQL `app.tenant_id` per tenant-scoped request and reset it after request handling.
- Add RLS policies for tenant-owned tables that already exist in the MVP model.
- Add tests for tenant creation, tenant listing, active tenant validation, role authorization, and cross-tenant isolation.
- Update only F03 RFC checkboxes backed by implementation and verification evidence.

**Non-Goals:**

- Do not build ERP, CRM, PDV, or Portal screens for tenant selection.
- Do not implement catalog, inventory, CRM, manufacturing, sales, or purchase domain CRUD.
- Do not redesign signup/login beyond what is needed to associate the user with tenants after authentication.
- Do not introduce organization billing, invitations, email flows, or external identity providers.
- Do not make future app permissions granular beyond the initial role gates required by F03.

## Decisions

### Use membership as the source of tenant access

Tenant access should be resolved from `tenant_users` for the authenticated user. Tenant listing returns only active tenants with a membership row for that user. Active tenant selection rejects tenants where no membership exists, even if the tenant id is valid.

Alternative considered: trust a tenant id supplied by the client and filter only in controllers. That is too weak for later modules because every endpoint would have to duplicate membership checks.

### Make active tenant explicit per request

Tenant-scoped routes should require an explicit tenant context, preferably through a documented request header such as `X-Supexon-Tenant-Id` after the user has selected a tenant. A dedicated selection endpoint may validate the choice and return the tenant plus membership, but API authorization should still validate the request header on each tenant-scoped request.

Alternative considered: store active tenant only in server session state. The API is JSON-first and token-based, so hidden session state would make typed clients and tests harder to reason about.

### Add middleware for tenant context and RLS session state

Create a named middleware for tenant-scoped routes that runs after auth. It should parse the active tenant id, verify membership, attach tenant/membership context to the HTTP context, and set `app.tenant_id` in PostgreSQL before downstream handlers run. It must clear/reset the setting in a `finally` block after `next()`.

Alternative considered: call a helper in each controller. Middleware gives one boundary for future domain routes and prevents silent omissions as F04+ endpoints are added.

### Keep role checks small and centralized

Roles are an enum-like contract in validation and authorization helpers. `owner` can perform all tenant/member actions; `admin` can manage operational members except owner-level transfers/deletions; `operator`, `seller`, and `viewer` cannot manage membership. Tenant creation makes the creator an `owner`.

Alternative considered: introduce a full permissions table now. The MVP only asks for initial roles, so a table-driven permission system would add migration and UI complexity before there is enough product evidence.

### Implement RLS as source migrations and policies

RLS should be added through source migrations that enable row-level security on tenant-owned tables and create policies using `current_setting('app.tenant_id', true)`. Non-tenant identity tables such as `users`, `tenants`, `tenant_users`, and token tables need deliberate handling: membership queries must remain possible through authorized application code, while tenant-owned domain rows must be isolated by `tenant_id`.

Alternative considered: defer RLS until domain CRUD exists. The RFC explicitly includes F03-US03 before F04+ APIs, and adding it now forces domain work to depend on the same request tenant contract.

## Risks / Trade-offs

- RLS can break application boot/tests if `app.tenant_id` is missing -> Mitigation: scope policies to tenant-owned tables, require tenant middleware only on tenant-scoped routes, and add tests for missing/invalid tenant headers.
- Resetting the tenant setting incorrectly can leak context across pooled connections -> Mitigation: set/reset in a `try/finally` wrapper and prefer transaction-local/session handling that is verified by isolation tests.
- Role semantics can drift if scattered across controllers -> Mitigation: centralize role constants and authorization helpers, then test representative owner/admin/non-admin paths.
- Generated contracts may change after route additions -> Mitigation: regenerate through existing build/typecheck commands and review generated changes without editing them manually.
- Full RLS coverage across every modeled table is broad -> Mitigation: inventory the existing `tenant_id` tables first and add policies systematically with tests against representative tables.

## Migration Plan

1. Add role constants/types, tenant and membership validators, and tenant context types/helpers.
2. Add tenant and membership controllers/routes under `/api/v1`, protected by auth.
3. Add the tenant-context middleware and apply it to routes that operate inside a tenant.
4. Add migrations/policies for RLS on existing tenant-owned tables.
5. Add functional tests covering tenant creation, accessible tenant listing, active tenant validation, membership role authorization, and tenant isolation.
6. Run API typecheck, build, test, and `openspec status --change implement-f03-identity-users-multi-tenancy`.
7. Update only F03 checkboxes in `docs/rfc-mvp.md` that have repository evidence.

Rollback is a normal commit revert. If RLS causes deployment issues, rollback the policy migration and API middleware changes together because the runtime contract and policies are coupled.

## Open Questions

- Should the active tenant validation endpoint be `POST /api/v1/tenants/:tenant_id/select` or a more REST-neutral context endpoint such as `PUT /api/v1/account/active-tenant`?
- Should owner transfer/removal be blocked entirely in the MVP, or allowed through a narrow owner-only route?
- Should `tenant_users.role` become a database enum/check constraint in this change, or remain a validated string until role semantics stabilize?
